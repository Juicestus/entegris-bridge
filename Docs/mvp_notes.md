# MVP extraction notes

Working notes for the pump / dispense / waveform extraction. Collected from the hardware runs of Oct 15, the
vendor docs in this folder, and the planning agent's MVP brief. Not yet the notes for the database team.

## Running it

    cd py
    python extract.py --config pumps.csv [--out out] [--save {0,1,2}]

- `--save 0` outputs only, `1` (default) also the raw capture of each cycle, `2` also every NCS request and reply
  under `runs/<run time>/comms/<address>/` with an `index.json`
- `python render.py <capture directory>` renders a saved capture again with no pump
- Each run pulls the newest cycle and the two before it, skipping any already collected clean. Only the newest
  gets the DISPENSE_INFO fields, the others say `header_available: false` and `cycles_behind`
- Bus damage: a chunk is retried up to `MAX_RETRIES` times, then repaired live only if exactly one flipped bit
  fixes it, the repaired reply is GOOD and the right size, and the trace then decodes to exactly `sample_count`
  samples. A repaired cycle has `reconstructed: true` and a `repairs` list. Every failed reply is kept as a
  `.bad` file in the capture
- A clean collection of a cycle replaces a reconstructed or blank one, never the other way round

## Decisions

- One to a handful of pumps, one after another. Each pump is self-contained in `extract_pump`, and pumps are
  grouped by bus (NCS and COM port), the unit that could run in parallel later
- `dispense.json` and `pump.json` are a superset of the tables: every column, defaults where we can't fill one,
  then extras
- Both dispense volumes are reported, the RTSTATUS setpoint and the LAST_DIS_INFO_2 measured value
- No hex on the terminal any more, `--save 2` replaces it. Legacy scripts lost their dumps too

## Outputs

- `pump.json`: one row of the pump table
- `dispense.json`: one row of the dispense table
- waveform CSV, the format profile_decode.py writes, later stored in GCS or S3
- Database IDs (`pump_id`, `dispense_id`) are generated by the database, so the dispense row points at its pump
  by `serial_number`
- Pump config is a CSV for now: address string, frequency in seconds, optional name. The address string is
  `addr:host:port:COMn`, parsed by `PumpAddress` in `py/pump_config.py`

## Design rules from the brief

- The raw capture is the source of truth. Collection only writes raw bytes. A separate render step makes the
  three artifacts from a capture directory and never needs a pump or a socket
- Key a capture on (pump serial, cycle number), both read from the pump. No invented IDs, no timestamps
- The brief said never repair during collection. We chose to repair live under strict checks and flag it, see
  above
- Absent columns are explicit nulls, not missing keys
- Re-rendering the same capture gives byte-identical output
- No new commands, no command number guessing. Only data fields inside confirmed reads vary
- Out of scope for MVP: parallelism, polling loop, database client, cloud upload

## Where each column comes from

Observed on pump ML08333, firmware V1011 Nov 08 2024. Use these as test vectors.

| pump_name | SVID 18 SystemNames.PumpName | TRK30 2-2 R3 FL955 |
| model_name | VERSION.Model, also SVID 10 | IntelliGen LV |
| firmware_version | VERSION.Version, also SVID 11 | V1011 Nov 08 2024 |
| customer_name | SVID 12 SystemNames.CustomerName | vendor export: "End user name" |
| fab_name | SVID 13 | Fab25 |
| tool_name | SVID 14 | TRK30 |
| coater_name | SVID 15 | 2-2 |
| nozzle_name | SVID 16 SystemNames.NozzleName | vendor export: R3 |
| resist_name | SVID 17 SystemNames.ResistName | vendor export: FL955 |
| fluid_name | SVID 19 SystemNames.FluidName | vendor export: "Fluid Name" |
| system_address | bus address from config | 2 |
| connection_details | config address string verbatim | 2:10.25.85.52:8888:COM8 |
| module_type | FIRMWAREINFO.module_type, an integer in a text column | 54 |

- The brief listed customer, nozzle, resist and fluid as not found. They are documented in
  `EntegrisSVIDS.pdf` (SVIDs 12, 16, 17, 19), we just never added them to `svid.REGISTRY`. The vendor export
  `SampleProfile.csv` from this same pump shows their values, so they exist on this pump
- Customer and fluid read as what look like factory placeholders, "End user name" and "Fluid Name". The fab
  hasn't filled them in. Worth telling the database team that a value can be a placeholder
- The pump name is tool, coater, nozzle and resist joined together, matching the separate fields
- The vendor export writes module type 54 as "Multi-purpose 4: FT-100 retrofit trigger recipe style", so a
  lookup from number to name exists somewhere, probably in the vendor docs
- SVID 20 Recipe.RecipeTitle and 21 DispenseInfo.JobInfo are also documented strings

### Dispense table

| Column | Source | Observed |
|---|---|---|
| cycle_number | DISPENSE_INFO.Cycle | 72123 |
| triggered_at | DISPENSE_INFO.Time, unix seconds, pump's own clock | 1792078934 |
| recipe_number | DISPENSE_INFO.RecipeNum | 1 |
| job_info | DISPENSE_INFO.JobInfo | Default Recipe One |
| reference_cycle_number | DISPENSE_INFO.ReferenceCycle | 43566 |
| firmware_version | VERSION.Version | V1011 Nov 08 2024 |
| sample_interval_ms | profile info SampleInterval | 5 |

- DISPENSE_INFO takes a recipe number, 0 means the most recent dispense. It can't be asked for by cycle. If the
  pump dispenses during a pull, the header can be for a later cycle than the waveform. Check its Cycle against
  the profile cycle, before and after the pull, and only pair them when they match
- `triggered_at` from DISPENSE_INFO and profile info Time agreed on every cycle we saw

## Gaps for the database team

Hard, the schema doesn't work without them:
- a link from the dispense row to its waveform object, like `trace_object_uri`
- `start_of_cycle_sample`, profile info StartCycle (400). The CSV time axis has no origin without it
- `sample_count`, profile info UnencodedSize. Varies per cycle, seen 2143, 2144 and 2145. Never hardcode

Worth adding:
- phase markers `dispense_end_sample`, `filtration_end_sample`, `fill_end_sample`, `end_of_cycle_sample`
- dispense volume. RTSTATUS.LastDispenseVol_uL read 800, which looks like the setpoint. LAST_DIS_INFO_2 read
  0.814 mL, which looks measured. The vendor export calls it TOTAL MOTOR VOLUME. Say which one is used
- confirmation percent, SVID 849 (99)
- ready pressure and reference ready pressure, slot id, from DISPENSE_INFO
- encoding and profile type, packed in Type_Encoding (257 is encoding 1, type 1)
- decoder version, a reconstructed flag, retries and bad frames for the capture
- the vendor export has a whole dispense confirmation block, each value for the cycle and for the reference
  cycle: ready pressure, correction volume, pressure and flow profile compare, max, average and cutoff
  pressure, motor rate, motor volume, air detect volume, filtration delta pressure, fill pressure. Some of
  this is probably in the unknown part of DISPENSE_INFO's reply

Semantic warnings:
- `job_info` is the recipe name, not a lot or wafer job. It won't join against work in progress data
- `triggered_at` is the pump's clock. Nothing syncs the clocks across the fleet. Record the host's time beside
  it so drift can be seen

## Hardware facts that shape the design

- Bus errors are normal: about one flipped bit per 5,700 bytes, both seen were the top bit of a byte. A
  profile is about 6,000 bytes, so many pulls will need a retry. The retry in the old test 3 pull handles it
- A reply with return code 29 is the same length as a good one and holds our request echoed back over the
  last profile info sent. It looks valid. Never parse a reply without checking its return code
- The pump keeps profiles for about 3 cycles: N to N-2 answered, N-5 refused. Cycle 0 answers as the newest
- This pump dispensed about every 140 seconds. A 300 second poll stays inside the 3 cycle window but only
  catches about every other dispense. To get every dispense, the interval has to be under one cycle period
- The flow sensor trace is zero for every sample, absent or broken on this pump
- Sanity check to keep: dispense position should move by about the dispense volume across the dispense
  window. It moved 0.811 mL against 800 uL set and 0.814 mL reported

## Open questions

- Does the gateway serve its COM ports in parallel? Untested
- Does the gateway allow reusing one TCP connection? Untested, matters at fleet scale
- Exact retention depth, somewhere from 3 to 4 cycles
- Can the reference profile be pulled? Asking for the ReferenceCycle value hasn't been tried on hardware.
  The brief says a candidate pull came back identical to the live profile, but that was test 4 pulling cycle
  72124, a live cycle that test 3 had also pulled, so it rules nothing out
- Config name vs the pump's own name: pump_name comes from the pump, the config name is a local alias. Confirm
- Poll interval would be better per pump in cycles than in seconds
